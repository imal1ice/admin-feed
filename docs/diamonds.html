Who can upgrade your EIP-2535 diamond?

admin-feed · a control-surface note by ownerwatch

A diamond (EIP-2535) splits a contract into facets whose code is replaced through diamondCut. That is its strength — and its blind spot. A diamond has no ERC-1967 implementation slot, so most admin-monitoring tools read it as a fixed, non-upgradeable contract and never watch diamondCut at all. The path that can replace any facet’s code is, by default, unseen by the monitors a protocol’s users rely on.

So the first question — for your own diamond, or one you depend on — is simply: who can call diamondCut, and with what delay?

Check it in one command

pip install ownerwatch
ownerwatch probe --prove --markdown --rpc https://ethereum-rpc.publicnode.com <yourDiamond>

ownerwatch resolves a diamond’s diamondCut gate and proves it by simulation — an empty diamondCut that succeeds from the gate and reverts from a stranger shows who really holds the upgrade power. It reports the full facet set and walks the control graph above the gate (owner → Safe → timelock → signers), the same for a diamond as for any proxy. Read-only; nothing is sent on-chain.

How to read the result

  • A single EOA on the gate — one key can replace any facet’s code (and often pause or change roles) immediately, with no delay. The chain shows an address, not how the key is held; an MPC or hardware setup looks the same, so confirm custody.
  • A Safe with no timelock — a multisig can swap facets in one transaction, no on-chain delay to watch.
  • A timelock in front — facet changes are queued and visible for the delay before they execute. The strongest shape.
  • No diamondCut exposed — the diamond may be effectively immutable, or use a non-standard gate; read the facets to be sure.

This is a chain view, not a verdict: it shows who can upgrade, not whether the team is trustworthy. The absence of a finding is not proof of safety — only that this read did not surface one.
